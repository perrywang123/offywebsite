# 独立站后台管理系统 · 设计

> 核心判断：**你真正需要的不是"一个后台"，而是一个补 Shopify 空白的运营控制台。**

---

## 一、先说不要做什么（能省掉 70% 的工作量）

你现在的数据分布是这样的：

| 数据 | 在哪 | 谁来管 |
| --- | --- | --- |
| 商品、价格、库存、图片 | **Shopify** | Shopify Admin ✓ |
| 市场、币种、发布范围 | **Shopify** | Shopify Admin ✓ |
| 订单、退款、物流 | **Shopify** | Shopify Admin ✓ |
| 政策文本（4 条） | **Shopify** | Shopify Admin ✓ |
| 支付、结账 | **Shopify** | 不该碰 ✗ |
| 头图文案、板块顺序 | **代码里** ✗ | **要改代码 + 发版** ✗ |
| FAQ 文案 | **代码里** ✗ | 同上 ✗ |
| 页脚文案、公告条 | **代码里** ✗ | 同上 ✗ |
| 商品在站上的编排（New Looks 取哪些） | **代码里** ✗ | 同上 ✗ |
| 用户行为数据 | **没有** ✗ | — |
| 加购/结算/订单事件 | **没有** ✗ | — |

**所以：以下这些千万不要自己做** ✗

- ❌ 商品增删改查 —— Shopify 已经做了，而且你在后台改了**网站会自动变**（我们全程都是实时读 Shopify ✓）
- ❌ 订单管理、退款、发货 —— 同上
- ❌ 库存管理 —— 同上
- ❌ 支付配置 —— 碰了会出事
- ❌ 多用户/角色/权限 —— 你就一个人用 ✓

**做这些等于花三个月造一个更差的 Shopify Admin** ✗

---

## 二、那真正缺的是什么

**只有四件事是 Shopify 覆盖不到、而你现在必须找开发才能做的：**

### ① 看数据（最高价值）

"哪些商品被点得最多"、"哪个页面 404 了"、"加购到结算流失多少" —— 这些 Shopify 看不到 ✓，也正是 `docs/analytics-mvp.md` 那套埋点在采的 ✓

**没有这个后台时**：你得找开发跑 SQL ✓
**有了之后**：打开一个页面就能看 ✓

### ② 改文案（第二价值）

改一句头图标题、FAQ 的一段、页脚一行 —— 现在要**改代码 + 提交 + 部署** ✗（我们有 5 分钟一版的发版流程 ✓ 但那也是有成本的 ✓）

**这块是唯一"必须动代码结构"才能解决的** ✗ —— 因为文案现在**硬编码在 `src/lib/content.ts` 和 `messages/*.json` 里** ✓

### ③ 编排商品（第三价值）

- 首页 New Looks 取哪些商品、取几款
- 名册里商品顺序
- 头图轮播的 5 屏顺序与内容
- 公告条在促销期换成什么

**Shopify 管不到这些** ✓（它只管商品本身 ✓）而你现在**改一次要发一版** ✗

### ④ 客户服务助手（第四）

客服收到邮件时要同时看：Shopify 订单 + 站上行为轨迹 ✓
现在这两边是**断开的** ✗

## 三、架构方案

### 推荐：**同一个 Next.js 应用里加 `/admin`** ✓

```
src/app/
  [locale]/          ← 现有站点（公开）
  admin/             ← 新增：后台（不在 locale 下，独立布局）
    layout.tsx       ← 侧边栏 + 鉴权守卫
    page.tsx         ← 数据看板
    content/         ← 文案编辑
    merch/           ← 商品编排
    events/          ← 行为流水
    login/page.tsx
  api/admin/         ← 后台专用接口（同样要鉴权）
```

**为什么不分仓/分应用** ✓：
- 复用现有的 DB / Shopify 客户端 / 类型 ✓
- 一次部署 ✓（不用维护第二套 CI/容器 ✓）
- 但**必须做隔离** ✗：`/admin` 不能进 sitemap ✓、要 `noindex` ✓、要有独立 layout（不带前台导航 ✓）

### 数据层改造：文案从"代码里"搬到"DB + 代码兜底"

```
读取顺序：  DB 覆盖值  →  代码里的默认值（fallback）
```

**这一点很重要** ✗：不能一上来就把代码里的文案删掉 ✓ 否则后台一挂、前台文案就空了 ✗

```ts
// 新增
contentOverride 表： key | locale | value | updatedAt

// 读取
function getHeroTitle(locale) {
  return getOverride("hero.title.streetwear", locale) ?? heroSlides.streetwear.title[locale];
}
```

**所有读取点都要走这层** ✓ —— 好处是：**后台没填就是用代码里的 ✓ 填了就用填的 ✓ 永不为空 ✓**

### 鉴权：单用户，所以简单做

| 项 | 做法 |
| --- | --- |
| 登录 | **一个密码**（`ADMIN_PASSWORD` 环境变量 ✓ 存 hash ✓ 不存明文 ✗） |
| 会话 | HttpOnly + Secure + SameSite=Lax 的签名 cookie ✓（`iron-session` 或自签 JWT ✓） |
| 过期 | 7 天 ✓ 可"退出登录" ✓ |
| 防暴破 | **登录失败限流**（同 IP 5 次/15 分钟 ✓） |
| 额外 | 可选：只允许特定 IP / 走 Cloudflare Access ✓ |
| **不要** | 不要开放注册 ✗ 不要多角色 ✗ 不要第三方 OAuth ✗（对单人系统是过度设计 ✗） |

**必须做**：
- `/admin/**` 全部 `robots: noindex` ✓
- `robots.txt` 里 `Disallow: /admin/` ✓
- 后台页面**不引用前台的任何公开组件**（避免样式/脚本互相污染 ✓）

## 四、四块功能的具体设计

### ① 数据看板（`/admin`）

基于 `analytics-mvp.md` 的表 ✓，展示：

```
今日：PV / UV / 加购数 / 结算数 / 成交额（成交额来自 Shopify webhook ✓）
趋势：近 7 / 30 天
Top 商品：被点最多的 10 款（点击 → 加购 → 成交 三段漏斗 ✓）
异常：今日 404 / 5xx 列表（**这个最实用** ✓）
```

**技术**：Server Component 直接查库 ✓ —— 不要做图表库集成 ✗（MVP 用表格 + 简单的数字卡 ✓ 够了 ✓）

### ② 文案编辑（`/admin/content`）

按"页面 → 区块 → 字段"组织：

```
首页 / 头图 / 第 4 屏 / 标题        [input]
首页 / 资讯区 / 主卡标题            [textarea]
FAQ / Part 1 / Q1 / 答案            [richtext]
页脚 / 法律声明                     [textarea]
公告条                             [input]
```

**必须有**：
- **长度上限校验** ✓（文案会撑破设计稿 ✗ 这是最容易出的事 ✓）
- **实时预览** ✓（用现有页面 + `?preview=` 参数 ✓）
- **草稿 → 预览 → 发布** ✓（不要"保存即生效" ✗ —— 改错一句就上生产 ✓）
- **改前改后 diff** ✓（出问题能一键回滚 ✓）

### ③ 商品编排（`/admin/merch`）

- **头图 5 屏**：顺序、图片、标题、跳转链接 ✓
- **New Looks 取哪些**：从 Shopify 商品里选（只存 handle ✓ 商品数据仍实时读 ✓）
- **名册顺序**：拖拽 ✓（存一个 `sortOrder` ✓）
- **公告条**：按时间段的促销文案 ✓

**注意**：这里**只存"引用"**（handle / id ✓），不存商品副本 ✗ —— 否则价格改了后台不知道 ✓ 会和 Shopify 不一致 ✗（这个坑我们已经在兜底表上踩过一次 ✓）

### ④ 行为流水（`/admin/events`）

按 session 聚合的用户轨迹 ✓ + 按路径聚合的错误列表 ✓

## 五、落地分期

| 期 | 内容 | 工作量 | 依赖 |
| --- | --- | --- | --- |
| **P0** | `/admin` 骨架 + 登录 + 鉴权守卫 + `noindex` | 3h | — |
| **P0** | 数据看板（先用 `pnpm analytics:report` 的数字 ✓） | 4h | **埋点 MVP 切片 1** ✓ |
| **P1** | 文案编辑 + `contentOverride` 表 + fallback 读取 + 预览 + 发布 | 12h | — |
| **P2** | 商品编排（头图 / New Looks / 名册顺序） | 8h | — |
| **P3** | 行为流水页 + 审计日志（每次改动记 who/what/when ✓） | 5h | 埋点 ✓ |

**共约 32 小时**，建议 **P0 先做** ✓ —— 3 + 4 小时就能给你一个"能看数据"的后台 ✓ 这是投入产出比最高的部分 ✓

**文案编辑（P1）是最值得的** ✓ 但也是最大的一块 ✓ —— 它要把 `content.ts` 的读取路径全部改造成"DB 优先、代码兜底" ✓ 涉及前台多处 ✓ 必须小心不要改坏现有页面 ✓（我们有像素比对的方法可用 ✓）

## 六、可选的第三条路：别自己写编辑器

如果你的核心痛点是"改文案要发版" ✗，那么另一条路是**接一个 Headless CMS** ✓：

| 方案 | 优点 | 缺点 |
| --- | --- | --- |
| **自己写** | 完全贴合、零月费、同一套代码 | 32 小时开发 + 长期维护 ✓ |
| **Sanity / Contentful / Payload** | 编辑器开箱即用、有草稿/预览/协作 | 月费 ✓ 多一个外部依赖 ✗ 要改数据层 ✗ |
| **Payload CMS（自托管）** | 嵌入 Next.js ✓ 免费 ✓ 有无头 CMS 的全部功能 ✓ | 引入一个不小的框架 ✗ |

**我的建议**：
- 如果你只想要"改文案 + 看数据" ✓ → **自己写 P0 + P1** ✓（够用、可控 ✓）
- 如果你以后要多人协作编辑、多语言内容管理 ✓ → **上 Payload** ✓ 别自己造 ✓

**现在这个阶段，自己写是对的** ✓ —— 你的内容量很小（几屏文案 + 10 条 FAQ ✓），上 CMS 属于杀鸡用牛刀 ✗
