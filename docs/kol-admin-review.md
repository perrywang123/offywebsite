# Offy KOL 后台方案复核 · V2.1

2026-10-31。对象：[完整方案V2.1](kol-admin-proposal.md)与静态原型。性质：业务/架构方案审阅，**不是已实现代码的安全审计，也不证明真实Shopify联调已通过**。用户要求的自定义佣金、Shopify权益逻辑、当次session、同机独立端口均作为本轮基线。

结论：旧草案存在边界缺口和过度实现，本轮已在V2设计中修订。方案可以进入整体确认；关键外部链路仍须在开发及上线验收中验证，不能报告“没有漏洞”。

## 已修订的设计缺口

| ID  | 优先级 | 原缺口/后果                                                | V2处理                                                                                         |
| --- | ------ | ---------------------------------------------------------- | ---------------------------------------------------------------------------------------------- |
| R01 | 高     | 固定5/8/10%档位不满足自定义；0%被当空值                    | 每人填写百分比，无默认档位；建议0–100、2位小数；0与未配置分开                                  |
| R02 | 高     | 按订单/事件到达时的当前比例计算，可能改写旧约定            | 创建checkout时锁定合作/规则版本、比例及有效期；后续变更不覆盖                                  |
| R03 | 高     | 在Offy编辑折扣/赠品并发布，重复实现Shopify规则且扩大写权限 | 权益规则归Shopify；同时支持已有绑定及生成新码同步，write_discounts受控使用，不重做赠品领取引擎 |
| R04 | 高     | 码活跃被误认为一定可用；可能承诺无法兑现的权益             | 摘要只读、按远端类型读取；实际适用性/履约由Shopify决定，品牌验证消费者承诺                     |
| R05 | 高     | 优惠码或旧Cookie补归因，违反只算当次session                | 仅当次链路，码不独立计佣；会话/checkout短期截止，回访不恢复来源                                |
| R06 | 高     | 全局最近KOL会被其他标签页覆盖；签名引用可被复制            | 每个checkout绑定服务端创建记录、比例与有效期，核验订单关联并一次消费；无证据待核查             |
| R07 | 高     | 用订单创建/支付授权/通知收到时间当成交                     | 已付款与成功交易类型/状态/处理时间联合核验；迟到消息不改变实际成交时间                         |
| R08 | 高     | Refund记录或退货申请一出现就扣佣，可能退款失败仍扣钱       | 核验退款交易成功；待处理/失败冻结核查，按成功商品退款分摊重算                                  |
| R09 | 高     | 含税市场、运费退款、礼品卡、应用赠品混算净额               | 按行项目折扣/税/成功商品退款拆分；免费行0，付费周边按真实净额；无法分摊不猜                    |
| R10 | 高     | 多币种相加、浮点或每次退款累积舍入可能错账                 | 同一交易币种、精确金额、按订单精度重算并记录差额，按币种分别结算                               |
| R11 | 高     | 锁单后退款仍按旧金额付款，或并发重复结算                   | 条目唯一约束/事务；锁定后有变化需重核对，付款前再检查；已付后记负调整                          |
| R12 | 高     | 新端口可从主站/admin或源站绕过，端口被当成登录权限         | 公网主站拒绝管理入口；内部端口loopback；逐请求鉴权、可信代理标记、HTTPS及访问限制              |
| R13 | 高     | webhook漏送/乱序、内存后台任务丢失，账本长期失真           | 持久化收件箱/重试、增量分页/重叠窗口核对、同步监控与失败时阻止结算                             |
| R14 | 中     | 停合作误停Shopify活动，或已付佣金退款无下一期可扣          | 本地状态与远端码状态分开；负余额保留待追回，不伪装已追回                                       |
| R15 | 中     | UV当人数、按天UV累加、码使用次数当转化率                   | 明确访问/到站/估算访客/成交会话/订单的分母与期间，首版不展示混合转化率                         |
| R16 | 中     | 只看本地历史快照假报已核对，默认60天权限不足               | 读历史订单权限按app配置；权限/同步失败阻止相关结算并显示更新时间                               |
| R17 | 中     | 容器重建丢数据、导出泄露客户资料/CSV公式注入               | 保留持久卷与恢复验证；最小字段、脱敏与导出转义，保留周期分别管理                               |

“已修订”仅指设计已补齐，不是这些机制已上线。

## 双入口发码补充复核

用户已确认两种方式同时支持，因此V2的“首版只读”取舍被替代，不回写历史归档。补充三项高优先级边界：

- R18：同一Shopify活动可对应多个KOL专属码，活动ID不能作为绑定唯一键；用店铺＋规范化码唯一，活动条件/总限额共用且只读展示。
- R19：异步任务提交不等于成功，必须核对具体代码结果并回读；超时待核对、重试复用原码，防重复发码及部分成功丢失。
- R20：远端成功但本地绑定失败要幂等补齐；待确认的新码不替换旧有效码，不为清理单码误删/停用共享活动。缺写权限时生成入口禁用，不谎报支持。

## 需要业务确认的参数

自定义佣金的输入范围/精度、是否只做百分比、站内无活动30分钟、checkout归因30分钟、付款冻结30天、按月按币种人工付款、Asia/Shanghai报表时区、流量90天的建议保留策略。用户已明确的“当次session计佣”和“优惠规则归Shopify”不再作为未决架构选项。

方案全文重写、旧约束交叉搜索、文档格式/本地链接/OpenSpec检查，以及原型的自定义输入、码绑定/错误态与桌面/窄屏复审。结果见 [原型验收记录](design/kol-admin/QA.md)。没有改业务运行源码、数据库或服务器部署，未运行生产Shopify操作。
