## 优先修复的问题

**P0：本次视觉证据未发现足以认定数据损坏或无法完成核心流程的P0问题。** 下面的P1需要在本轮完成，尤其保存操作不应以按钮勉强还能点击作为通过标准。

**P1-1：订单筛选不是完整的字段体系。** `AdminConsole.tsx` 的三个下拉只有 `aria-label`，无可见标签；日期有标签且 `.filters label` 为11px，`.filters input` 又覆盖为透明背景。相同任务的控件因而呈现不同层级。三个下拉固定180px、日期依赖最大190px，无法随内容区域形成稳定栅格。应把所有筛选封装成同一种“标签+控件”字段，统一白底、44px高、13px标签及12px列间距；把日期视为一个时间范围组，提供清楚的开始/结束含义。

**P1-2：手机弹窗页脚遮挡字段且保存按钮被裁切。** 手机新增合作截图可直接看到底部保存按钮贴住弹窗下缘，按钮文字/下半部接近被切掉；正文中的合作状态又被页脚覆盖。源码 `.dialog-actions { position: sticky; bottom: -20px; ... }` 使页脚依赖表单正文滚动和负偏移。应改为弹窗三段结构：固定头部、唯一可滚动正文、独立且完整可见的操作区；不得用负 bottom 定位。正文必须能滚动到最后一个字段，且最终字段和错误提示不被页脚遮挡。

**P1-3：手机页头把主要内容让给次要操作。** `page-heading` 始终左右排列，右侧“连接与同步”“退出登录”占掉横向空间，375px截图里的说明因此被切成短句；导航本身又占约190px，用户尚未开始查找资料就已消耗大半首屏。手机应分成完整宽度的标题说明和单独的工具行；将退出收进账户区域或明确的次级入口。五个栏目必须全部可发现，不能以不可见的横向滚动代替完整导航。

**P1-4：中间宽度缺少可确认的内容边界。** 所有表格统一 `min-width:850px`，而诊断网格采用多列最小值，正文容器还保留侧栏及左右内边距。在约901px等侧栏刚出现的宽度，诊断网格最小宽度可能大于可用空间；合作行也依赖硬编码跨列与 `nth-child`。这在现有截图中尚未完整验证。研发应先测900/901、1024、1280，再决定切换点；列表内容只能在明确的表格滚动区内横向移动，页面本身不得横向溢出。

**P2-1：空态过于高大，弱化了下一步。** 通用 `.empty` 采用250px最小高度与64px上下内边距；优惠码页同时具有“优惠码”和“发码任务”两块空态，会让用户在两块白色大容器之间滚动。首个无数据状态应说明下一步并提供同名主操作；筛选无结果应提供“清空筛选”；子区空态应为紧凑说明行，避免再次占据整块首屏。去掉没有业务含义的斜箭头，不额外增加插画。

**P2-2：表格类型没有分别设计阅读节奏。** 合作名单、订单、优惠码和月结有不同主键与动作密度，却共享过宽的最小宽度、相近的单元格大间距和多按钮并排。数据多时会产生大量横向扫描；数据少时显得空。应以“名称/单号—状态—核心金额—主动作”为第一阅读层，时间、活动ID和技术原因降到可展开的第二层。金额按币种分别核对，数字列右对齐、使用等宽数字，不隐藏负数、不混币合计。

**P2-3：关键信息存在过小字号。** 表头、徽章、筛选日期标签、错误原因当前有11px；移动页头连接按钮10px，页脚9px。原契约要求辅助信息最小12px，当前执行不一致。业务标签、时间、状态与原因至少12px，表格正文13–14px，交互正文14px；装饰性编号可更小，但不能承载唯一操作线索。原始JSON与长ID应可展开、可复制、可换行，不直接替代人能理解的结果描述。

**P2-4：主要、次要和有后果的操作缺少统一视觉层级。** 表格中的“复制”“核验”“结束绑定”“取消/重建”等多为相同边框按钮，仅靠用户读完文字识别后果。保持每行一个主要操作，普通次级动作用文字或浅边框，有后果的操作使用明确的危险文字和确认文案。红色只用于错误/危险，不将例行“待核查”都标红。

## 给研发的修订契约

视觉命题仍是“可核对、轻量的 OFFY 合作账簿”。保留暖灰底、白色内容表面、墨色主要文字/操作、灰色次级说明；深绿用于已核验，橙褐用于待处理，红色用于明确错误或危险。继续使用系统字体和现有技术栈，不引入外部字体、图表面板或通用仪表盘装饰。

1. **统一基础字段。** 每个搜索/下拉/日期都有可见且关联的标签。基础高度44px，圆角6–8px，边框一套、白底一套，左右内边距12px；只读和禁用另有状态。标签与控件间隔6px；字段和动作之间间距12px。原生日期控件保留可用性，不能隐藏日期选择图标来装饰。
2. **按内容宽度决定筛选布局。** 宽屏可把KOL、币种、状态、起止日期放同一字段行，搜索与页面主动作明确分组；空间不足时整组按两列/单列降级，不能先把日期压到看不见值。320–540px的主搜索独占一行；其他筛选最多两列，日期可成对或各自整行。禁止用固定宽度撑出页面横滚。
3. **规范页头与工作区。** 桌面标题区到工作区24px，工具栏到结果16–20px；标题不额外堆大面积留白。手机标题区占满宽度，次级账户动作单独成组；主操作与刷新不夹在标题说明之间。刷新按钮有固定最小宽度，文案变化不推动相邻操作。
4. **规范弹窗。** 桌面常规宽度640–720px，诊断宽度可到960px；最大高度 `min(90dvh, …)`，头/正文/页脚分离，只有正文滚动。手机左右至少12–16px，页脚留安全区，所有主按钮44px以上完整可见。错误提示可定位、不会被头部遮住；关闭与返回焦点保持原有行为。
5. **规范列表与空态。** 数据列表占主要工作区，子区不用重复大空态。表格头12px、正文13–14px，主要标识有足够对比；行操作允许有边界的横向滚动，滚动区域可键盘到达并有名称。手机优先有标签的记录摘要，确有列比较必要的表格再横滚。
6. **可读而可核对。** 长名称、长码、长URL、多个商品、负金额、大金额、缺省时间都应有自然换行或局部滚动策略。不得为保持齐整把真实金额截断、把状态只显示为颜色，或用假数据补空白。

## 必须提供的复测证据

所有数值是验收标准，当前报告不宣称它们已经实现：

- 360×800、375×812、768×1024、900×900、901×900、1024×768、1280×900、1440×900、1920×1080：页面 `scrollWidth <= clientWidth + 1px`；局部表格滚动另行检查。
- 所有常用可点击目标至少44×44px；必填/可选、可用/禁用、hover/focus、错误和更新中都有可识别状态。相同筛选行的控件顶/底边差不超过1px，标签到控件间距一致。
- 375px弹窗首屏/中段/末段分别截图；焦点滚到任意字段时控件完全可见，页脚与字段无交叠；保存按钮不被弹窗底边、软键盘或安全区裁切。
- 用明确标注的隔离样例分别提供五栏目“有数据”与“无数据/无匹配”截图，至少包含40字符姓名、64字符优惠码、长活动ID、多商品诊断和负佣金调整；不能只用空库认定表格完成。
- 键盘完成切页、筛选、清空筛选、打开/关闭详情；200%缩放和减少动效下仍能理解当前页、状态及主操作。
- 修复后沿同一评分表重评，目标85/100以上；P1-1至P1-4均无未解释的失败项。不得仅凭分数上涨绕过保存按钮、日期可读性或页面溢出问题。

研发可据此与交互专项报告合并，先形成一份冻结的实施清单和 OpenSpec，再修改源码和测试。最终评分应依据新截图与实际操作重新给出，不直接沿用本次建议分数。

1. **手机诊断和通用页头仍可更紧凑。** 品牌、两行导航、标题说明、账户工具、诊断提示与统计工具相加后，首条诊断记录仍接近首屏下缘。当前可用且没有遮挡，后续可测试把账户工具收纳、将次要说明更紧凑地展开，避免再次扩大本轮范围。
2. **长技术信息仍占较多阅读空间。** 64字符码、活动ID、多个商品handle与日期说明均可读但行高较大；后续可提供更清楚的摘要/展开方式。任何压缩必须保留复制入口、完整核对能力和真实负号/币种，不应直接截断金额或只留下颜色状态。
3. **部分阅读密度与动作语言尚可细化。** 诊断查询/刷新为两个动作、复杂记录的次级信息较多；确认按钮仍可根据具体动作进一步命名。属于继续提升效率的P2，不影响当前目标辨识与操作可达。
