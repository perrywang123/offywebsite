# Offy KOL 合作后台完整方案 · V2.1

状态：**用户已批准并完成首版实现；默认关闭，未部署生产**。实施范围/差异见 [验收记录](kol-platform-validation.md)，操作与限制见 [运行手册](kol-platform-operations.md)。更新日期：2026-10-31。配套 [交互原型](design/kol-admin/index.html)、[方案复核记录](kol-admin-review.md)。本版保留自定义佣金、当次session及独立端口，并按用户确认同时支持「绑定Shopify已有码」和「Offy生成新码并同步」。优惠规则仍由Shopify维护。

当前项目已有 Next.js 15、Shopify Storefront/Hosted Checkout、SQLite/Drizzle、Docker 部署配置；已新增KOL专项管理员、访问链路、Shopify财务核对及人工结算。HTML原型仍为演示，正式实现见运行手册；不将原型数据当成真实账目。

## 1. 已明确的要求与本版建议

**用户已明确：**

- 给品牌管理员使用，界面简单，KOL不需要登录。
- KOL通过专属链接推广；**仅当次session链路内的购买计作转化**，取消30天跨会话追踪。
- 佣金支持自定义，不限制在5%–10%。
- 优惠码支持两种方式：绑定Shopify已有码，或Offy生成新码并同步到Shopify；权益规则仍由Shopify维护，码不独立产生或覆盖分佣归属。
- 后台与独立站在同一套服务器；后台使用独立访问端口，能够读取独立站服务端写入的数据。
- 新增KOL只操作数据库与后台，不为每个人新建页面或重新部署。

**本版参数已随整体方案获准实施：**

| 项目       | 第一版建议                                                                        |
| ---------- | --------------------------------------------------------------------------------- |
| 自定义佣金 | 每次合作填写百分比，0%–100%，最多2位小数，必填且无默认8%；不是固定金额/阶梯佣金   |
| 优惠码职责 | 已确认双入口：绑定已有，或选择Shopify活动生成新码并同步；需读取及受控写入优惠权限 |
| 会话边界   | Offy站内连续30分钟无有效活动结束；进入Hosted Checkout时登记30分钟结账归因截止时间 |
| 比例快照   | 在服务端创建该次Shopify Cart/checkout时锁定合作版本和佣金比例；修改仅影响后续结账 |
| 冻结与支付 | 实际付款后冻结30天，每月按KOL与币种结算；品牌线下付款，后台登记凭证               |
| 部署       | Nginx分开主站入口与后台HTTPS端口，内部共用一个应用和数据库；8443仅为示例          |

会话的30分钟和佣金冻结的30天是两件事；会话超时不恢复历史来源，佣金冻结只是退款核对期。比例范围与小数精度是输入约束建议，不是固定商业档位；0%表示有效归因但应计佣金为0，与“尚未设置比例”区分。

## 2. 完整业务流程

1. 管理员登录后台，新增KOL及合作，填写自定义佣金、合作日期、社媒与联系信息。
2. 如需粉丝权益，可绑定Shopify已有码；也可在Offy选择Shopify已有的折扣码活动，生成KOL唯一代码并同步，远端确认成功后绑定。未绑定优惠码也可开展链接分佣。
3. 后台生成 `/r/maya` 等链接，复制包含链接、码和合作条件的合作包，品牌自行发送给KOL。
4. 粉丝点击链接，Offy校验合作并记录访问、建立本次session，跳转正常商品/集合页面。
5. 粉丝在当次session发起结账，服务端保存归因与比例快照，创建Shopify Cart并带入可核验的链路引用。
6. 粉丝在Shopify最终结账使用优惠码。Shopify判断权益是否适用，并处理付款、订单、退款与履约。
7. Offy通过服务端事件及主动核对取得订单/交易事实，核验当次链路，计算佣金并先冻结。
8. 冻结结束后生成结算草稿，重新核对Shopify、锁定清单、导出对账单；线下付款后登记流水。

已另建行为OpenSpec并按TDD实现；本次使用隔离测试库/Shopify模拟器，不修改真实店铺或生产服务器。

## 3. 管理后台：四个页面

| 页面       | 核心操作                                                          | 关键字段/指标                                                                                        |
| ---------- | ----------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------- |
| 合作达人   | 新增、编辑、暂停、查看详情、复制合作包                            | KOL身份、平台、合作状态/日期、自定义佣金、推广链接、当前码、访问/到站/估算访客、已付款净带货额、佣金 |
| 优惠码管理 | 绑定已有码、生成新码并同步、查询任务/重试、刷新状态、结束本地绑定 | KOL、原始码/远端ID、Shopify标题/状态/有效期/只读摘要、最近同步时间、绑定历史                         |
| 订单佣金   | 按KOL/日期/币种/状态筛选、看计算依据、审核异常                    | Shopify单号、链路证据、商品净额、退款、比例快照、佣金、冻结到期、审核与调整记录                      |
| 月度结算   | 草稿、核对、导出、锁单、记录付款/更正                             | KOL、币种、期初调整、本期佣金、订单清单、应付/已付、付款流水与审计                                   |

默认进入合作名单，内部中文，面向粉丝的文案英文。桌面优先，手机可查账、复制链接与查看清单。连接状态和少量全局规则放页头/抽屉，不增加复杂BI或独立设置中心。

所有页面区分加载、真实空白、筛选无结果、权限过期与同步失败；未知金额显示“—”，不同币种不合计。给KOL的CSV不包含买家邮箱、电话、地址；CSV文本字段处理公式注入，数字字段采用稳定格式。

### KOL与合作资料

- 必填：展示名、社媒账号/主页、平台、联系邮箱、佣金比例、合作起止。启用前检查别名唯一、比例有效、日期顺序；未配置比例的草稿不能产生结账归因。
- 可选：合同文件链接与签署状态、视频数量/交付截止、已发布视频URL、寄样说明、收款方式/脱敏账号与备注。不做电子签、社媒抓数或自动消息。
- 同一KOL保留稳定ID；合作条款按版本记录，续约或改比例不覆盖旧版本。
- 状态：草稿 → 合作中 → 暂停/到期。正常暂停/到期停止新推广链路及新checkout；已创建的有效checkout可在原短期截止时间内完成。历史佣金保留；违规争议订单只能带原因冻结，不能删除账本。
- 暂停合作**不自动停用Shopify优惠码**。界面明确提示品牌到Shopify处理权益，避免把本地状态冒充远端状态。

### 自定义佣金

第一版为「百分比 × 商品净额」，例如7.25%、12%、18.5%；可以0%，不预设8%或限制5%–10%。建议存成整数万分比，7.25%=725，使用精确十进制/币种精度计钱。

创建checkout时由服务端锁定：KOL、合作版本、比例、规则版本、计佣范围与时间。用户提供的金额/比例不能写入快照；仅保存客户端可修改的cart attribute不构成可信证据。若创建失败并重试，使用对应的持久化创建记录防止来源或比例重复覆盖。

## 4. 推广链接：一次部署，新增合作即时生效

统一动态入口拟为 `src/app/r/[alias]/route.ts`，按请求查询数据库：

```text
/r/maya → Maya的有效合作 → 新建本次推广链路 → 站内目标页
/r/eli  → Eli的有效合作  → 新建本次推广链路 → 站内目标页
```

新增KOL只新增数据，后台自动拼接链接，不生成独立页面、不重建镜像。别名大小写/字符集统一校验并设唯一约束；历史别名不转给其他人。目标只允许配置的站内路径，不接受任意外部redirect。不存在、暂停或到期的链接说明合作入口不可用，并可继续浏览商店，不建立佣金归因。

链接入口及跳转不静态缓存；禁止CDN缓存绕过记录/合作校验，排除已知预取、链接预览、机器人与HEAD请求。不能可靠识别所有机器人，后台不把请求次数称为精确自然人数。

`/?ref=maya`同样可做动态识别；`/#maya`需要前端读取再上报，因为fragment不随HTTP请求发送服务器，因此本版继续推荐 `/r/maya`。[Next.js动态路由](https://nextjs.org/docs/15/app/api-reference/file-conventions/dynamic-routes)、[MDN fragment说明](https://developer.mozilla.org/en-US/docs/Web/URI/Reference/Fragment)。

## 5. 优惠码：两种方式都支持

**已确认：绑定Shopify已有码，以及Offy生成新码并同步。** 管理页提供两个并列入口，共用历史绑定与状态清单。Offy不编辑优惠比例、赠品SKU、领取、门槛、叠加或履约逻辑；这些仍在Shopify或对应应用维护。

### A. 绑定Shopify已有码

1. 选KOL，粘贴已在Shopify创建的码。
2. 服务端读取并核对店铺、规范化码、所属活动ID、远端状态与规则摘要。
3. 检查本地绑定归属；码按Shopify大小写不敏感处理。只有校验通过才保存绑定；未知/超时/无权限不能假报成功。
4. 支持复制、读取远端状态及结束本地绑定。换码保留历史，已绑定码不重新分配给别的KOL。

Shopify原生后台可在「折扣 → 创建折扣 → 方法选折扣码」输入或生成代码。[官方中文步骤](https://help.shopify.com/zh-CN/manual/discounts/discount-types/percentage-fixed-amount)。

### B. Offy生成新码并同步

1. 选KOL及一个**Shopify已有、已验证可追加代码的折扣码活动**，只读展示摘要、期限及共享限制；自动折扣不能当作有码活动选。第三方应用活动若本店API不支持追加，禁用该选项并可改走A。
2. Offy按KOL别名生成唯一候选码，也允许管理员修改；本地与Shopify都查重，使用规范化唯一键。暂停/到期合作不能新发码，草稿可准备，尚未启用不对外推广。
3. 先持久化发码操作ID、店铺、KOL、活动ID和候选码，保留本地占用记录；点击确认后通过Admin API写入Shopify。
4. 首版每次为一位KOL发一个码，调用 [discountRedeemCodeBulkAdd](https://shopify.dev/docs/api/admin-graphql/latest/mutations/discountRedeemCodeBulkAdd) 向活动追加代码；该接口异步，HTTP成功或拿到任务ID不等于码已经创建。
5. 持久化远端任务ID，通过 [discountRedeemCodeBulkCreation](https://shopify.dev/docs/api/admin-graphql/latest/queries/discountRedeemCodeBulkCreation) 核对完成状态、具体代码的结果与错误，再回读核验代码、店铺及活动ID。
6. 远端确认成功后，以事务完成KOL绑定并更新当前可分发码。此前的新码保持“同步中/待核对”，不进入可用合作包，旧的有效绑定不被覆盖。

发码状态：草稿 → 同步中 → 远端确认并绑定；确定失败显示原因并允许重试；超时/响应丢失显示待核对，不立刻当失败、也不直接另生成一个码。重试复用同一操作ID和候选码，先核对远端，避免一人重复发码。远端已成功而本地绑定失败时保留“待完成绑定”，恢复后幂等补齐，不能删除整个活动来清理一个码。

不同KOL可能使用**同一个活动ID下的不同代码**：唯一约束按店铺＋规范化码建立，不能把活动ID本身设为唯一。多个代码共享所属活动规则，可能共用总使用额度/期限；Offy不虚构每个码独立的限制。若需独立条件，品牌应先在Shopify建立独立活动再选择。

### 共同边界

- 活动/规则摘要依旧只读。Shopify [codeDiscountNodeByCode](https://shopify.dev/docs/api/admin-graphql/latest/queries/codeDiscountNodeByCode) 可查金额、买赠、免运费及应用提供的优惠；无法解析的应用规则提示到Shopify查看，不猜权益。
- 完整双入口需要查询与 `write_discounts` 写入权限。未授权写入时禁用“生成新码并同步”，A在读取权限有效时仍可用；本轮不实际增加店铺权限或创建真实优惠。
- 绑定来源记录为“Shopify已有/Offy生成”，保留活动ID、任务与操作记录。结束本地绑定或暂停KOL不自动停用Shopify码；同一活动可能服务多人，尤其不能一键停整个活动冒充停一个KOL。
- “远端确认/活动中”不代表对每个购物车适用。商品、市场、门槛、客户等条件由Shopify判断；如未来自动预填需查 [CartDiscountCode.applicable](https://shopify.dev/docs/api/storefront/latest/objects/CartDiscountCode)。本版仍先由粉丝在Shopify输入码。
- 合作包不自动承诺“10% off/自动获赠”。品牌按已核实活动填写说明。原生买赠不会自动把赠品加进购物车，具体承诺由Shopify活动/所用应用的配置验收覆盖，Offy不重做领取引擎。[官方买赠说明](https://help.shopify.com/en/manual/discounts/discount-types/buy-x-get-y)。
- 优惠码与当次链接归因分离：只用码不计佣，Maya链路使用Eli码也不把佣金转给Eli。码使用次数不是KOL带货订单数。

## 6. 归因：仅当次session链路

| 购买过程                                  | 订单归属                                           |
| ----------------------------------------- | -------------------------------------------------- |
| 点击Maya链接，在当次有效链路内完成购买    | Maya，无须使用优惠码                               |
| Maya链路使用Maya码、Eli码、品牌码或不用码 | 仍归Maya，金额按Shopify实际结果                    |
| 没点推广链接，只使用KOL码                 | 不产生KOL转化或佣金                                |
| 会话结束，之后直接回访购买                | 不追溯历史来源                                     |
| 再点一次Maya链接，在新链路购买            | 按这次新链路归Maya                                 |
| 创建checkout前改点Eli链接                 | 后续由新链路创建的checkout归Eli                    |
| Maya的checkout已创建，别的标签页又点Eli   | Maya原checkout保留自己的来源；不被全站最近点击覆盖 |
| 来源、会话、checkout或订单无法核验        | 待核查，不凭码或浏览器“成功页”补认领               |

### 明确的会话参数建议

- Offy站内连续30分钟没有有效活动，session结束；正常导航、刷新及加购可以延续有效session，不以无人操作的后台心跳无限续期。
- 在有效session发起Shopify结账时，登记独立checkout引用与**创建后30分钟**的归因截止时间。跳转Shopify不立即结束链路；超时后的旧结账恢复不沿用KOL。
- 按Shopify实际订单/成功付款时间核验是否在本次checkout有效期内，不能用webhook到达时间。支付待处理、延迟扣款、分次付款等不能证明当次全额成功的情况先待核查，不静默认佣。
- 不使用30天持久化referral，不跨设备拼接。浏览器关闭通知不可靠；短期会话标识辅助连续性，服务器有效期负责判定结束。不能承诺准确检测“离开网页的瞬间”。[MDN sessionStorage说明](https://developer.mozilla.org/en-US/docs/Web/API/Window/sessionStorage)。

服务器保存session/链路、KOL、合作版本、checkout ID与有效期。传入Shopify的引用需签名并绑定具体cart/checkout及一次性创建记录；订单ID只消费一次，重复事件不重复归因。签名只证明引用未被修改，仍需核对本地创建记录和订单关联，防复制/重放。

同一KOL的会话可以产生多笔真实订单，但每笔必须有独立、可核验且未过期的checkout；后台另显示成交会话数。新建checkout时重新校验合作是否有效。无法采集或保存来源时购物不被统计故障阻断，后台告警并将相关订单列为待核查；只有确凿服务端证据才可人工补记，并留审计，不用码兜底。

## 7. 访问与带货指标

| 指标                      | 口径/来源                                              |
| ------------------------- | ------------------------------------------------------ |
| 推广链接访问次数          | Offy入口记录，过滤已知无效请求；不是精确人数           |
| 到站访问次数              | 落地页加载确认，按访问ID去重                           |
| 可识别访客数（估算）      | 允许使用匿名标识时，在所选期间去重；无法去重单独标注   |
| 成交会话数                | 对应期间内至少有一笔合格已付款订单的推广session数      |
| 有效订单数                | 当次链路可核验且已付款的订单，区分全退/部分退款/取消   |
| 净带货金额                | 合格订单的商品折扣及成功退款后净额，按币种展示         |
| 应计/冻结/可结算/已付佣金 | 逐订单账本与结算记录汇总，不能只以订单总金额乘当前比例 |

日去重数不直接相加为月去重数；点击日期与付款日期分开筛选，不把不同日期队列相除。首版不强推一个混合“转化率”：订单数不是人数，退款、跨期付款和无法去重都影响分母；若显示，必须明确是同批到站session的付款转化，且标明观察截止时间。流量不参与计佣。

净带货金额按付款日期筛选，扣减截至查询时已同步的成功商品退款，标明“截至最后同步时间”；它可能随后续退款变化。已锁定结算单保留当时快照及后续调整，不能用当前统计覆盖旧付款凭证。

时间存UTC，后台日期筛选/结算周期建议统一Asia/Shanghai并显示时区；Shopify优惠自身有效期以远端返回时间为准。仅最小KOL流量采集，不先建设全站埋点平台；不保存原始IP、不做指纹去重。原型演示不代表已采集真实数据。

## 8. 计佣、退款与币种

**订单应计佣金＝可计佣商品净额 × 创建checkout时锁定的自定义比例。**

商品净额从Shopify行项目、折扣分摊与成功退款得出；排除税、运费、关税、独立费用及礼品卡商品。税已包含在价格的市场要按Shopify税字段扣除商品税，不能把含税价直接当税前净额。免费行项目净额为0，自然不计佣；不能因商品名叫“周边/赠品”就把其实际付费部分一概排除。礼品卡/余额作为付款方式不减少商品计佣基数。

例：商品税前USD100，Shopify实际优惠后商品净额USD90，比例12.5%，佣金为USD11.25。随后成功退回USD30商品净额，剩余基数USD60，佣金为USD7.50，记录−USD3.75调整。税、运费及其退款不混入商品退款扣减。

- 只认已成功收款，不把订单创建、支付授权或浏览器返回页当付款。实际支付状态/时间按 [OrderTransaction](https://shopify.dev/docs/api/admin-graphql/latest/objects/OrderTransaction) 的类型、状态与处理时间核验；退款后看到的订单当前状态不能抹掉历史成功付款事实。
- **Refund对象存在不代表已退钱**，需核对关联退款交易状态；待处理/失败先冻结相关佣金，成功后再调账。退货申请/退回库存也不等同已退款。[Shopify退款说明](https://shopify.dev/docs/api/admin-graphql/latest/objects/Refund)。
- 全额商品退款应计归零；部分退款重算剩余应得金额，按“新应得−已记账”入调整，防止重复消息或多次小额退款重复扣减。
- 未付款取消不计佣；已付款取消、订单编辑、拒付/争议、非行项目补偿、退款分摊不明先冻结核查，不按总退款金额猜商品净额。
- 拒付事件与权限按实际支付渠道联调；无法完整自动覆盖的渠道，付款前列为明确的人工检查项，不能显示为“已自动审核无风险”。
- 用精确十进制/币种最小单位，按订单及币种精度四舍五入（half up）；不要用浮点数直接算钱。零比例可显示0.00，不当成缺失；净额或退款不一致时停止自动结算。
- 使用Shopify订单交易币种的presentment金额；行项目、折扣、税、退款需同币种。USD/GBP/HKD分开出单，不自动相加/换汇，不从商户收单结算币种反推佣金。
- 历史比例、币种和依据不可静默覆盖。修正归属/金额要保留前后值、理由、操作者、时间及关联证据。

## 9. 冻结、月结与人工付款

建议：成功付款时间起冻结30天，期满且无异常才可结算，每月生成一次已到期佣金清单。该默认值待确认；冻结期与KOL链接session有效期互不影响。

状态按「应计/冻结中 → 可结算 → 结算单锁定 → 已付款」管理；异常有独立冻结状态。结算单按KOL＋币种＋批次保存。

1. 生成草稿：列出到期未结算佣金、历史负调整与应付余额。
2. 锁单前：重新向Shopify核对所有相关订单/退款，并显示最后核对时间；有失败/待核查则不能锁定受影响条目。
3. 锁定：事务及唯一约束确保一笔有效佣金条目不进入两张生效结算单。锁定后金额变动标记“需重核对”，不能照旧付款。
4. 转账前再次检查锁单后的变更/退款；品牌自行完成银行或PayPal等线下转账，系统不自动打款。
5. 登记已付：日期、实际金额/币种、流水号及凭证引用。登记不等于调用转账接口；不接受应付与实付不符而无说明，首次只支持整单登记付款。
6. 迟到退款：未付单需要重新核对/解锁重出并留记录；已付款保留历史，下一批记负调整。KOL结束合作且无下一批时显示待追回应收，人工处理，不假装负余额已追回。
7. 误记付款通过撤销/更正记录修复，保留原记录；不删除账本。无最低打款门槛，负余额结转。

锁单核对不能阻止之后在Shopify发生退款，因此仍需持续同步和后续调整；不能承诺跨系统的绝对原子付款。

## 10. 同服务器、独立访问端口、共用数据

推荐首版是**两个访问入口、一个内部应用、一份数据库**。端口号只决定访问入口，数据由应用写进数据库，不“保存在端口里”。

```text
粉丝 → 主站HTTPS入口 → Nginx公开路由 → Docker内Offy应用 ─┐
                                                        ├→ /data/offy.db
管理员 → IP:独立HTTPS端口 → Nginx后台入口 → 服务端鉴权 ──┘
```

- 主站保持现有域名/端口；后台例如 `https://服务器IP:8443/admin`，8443只是示例。后台专用入口只开放必要的后台、登录及资源；公网主站拒绝后台页面、管理API与旁路请求。
- 应用继续绑定宿主机 `127.0.0.1:3000`，数据库沿用 `offy-data:/data`。后台服务端函数直接通过共用数据层查询已提交记录，不读公开网页、不复制两套DB、不为首版增加RPC。
- 推广访问由Offy写入；Shopify付款/退款经事件与核对入库；后台读同一份记录并显示更新时间。商品展示继续以Shopify为准，本地订单账本不恢复商品fallback。
- schema在 `src/server/db/schema.ts`，访问层在 `src/server/db/client.ts`，新增业务集中 `src/server/kol/`；迁移由一处管理。SQLite单应用首版适配，但需验证WAL、写事务、超时、短查询和实际数据量；先不假定要迁PostgreSQL。
- 容器重建保留持久卷；备份须包含一致性数据库状态，验证恢复。不能用删除volume排障。日后真拆独立进程/容器，再设计内网RPC/共库权限、迁移归属与并发，不把新增访问端口误当成必须拆应用。

**访问控制：**

- 独立端口仍可能被扫描；需有效HTTPS、管理员登录、登录限流/过期/退出撤销/审计，建议管理员IP白名单。IP形式访问需证书覆盖该IP；也可用管理域名＋端口配置证书。
- 每个管理API、Server Action与服务端数据函数都校验身份/入口，不只隐藏导航。主站入口、未知Host、直接访问源站/3000、编码/尾斜杠/locale路径等旁路都纳入验收。
- 仅信任受控代理覆盖写入的入口标记，不接受外部自行传入的Host/Origin/“管理员”头作为身份。状态变更校验可信Origin/CSRF；cookie使用Secure/HttpOnly及适当SameSite，管理员与粉丝session分开。不同端口不能代替会话隔离。
- Shopify webhook在公开、独立验签的入口接收，不被后台访问限制误拦；数据库及真实密钥不公开。新增配置统一经 `src/lib/env.ts`。

仓库已增加双入口Nginx模板与worker配置，**尚未在生产部署或开放后台端口**。[Docker端口说明](https://docs.docker.com/get-started/docker-concepts/running-containers/publishing-ports/)、[OWASP逐请求授权原则](https://cheatsheetseries.owasp.org/cheatsheets/Authorization_Cheat_Sheet.html)。

## 11. Shopify同步、权限与运行保障

1. 服务端按原始请求体HMAC验签并核对店铺，事件持久化收件箱后再确认接收；去重、重试和处理状态可见。
2. 付款/订单更新/退款/取消等事件触发读取订单最新状态；不能按到达顺序直接加减总额。事件可能重复/乱序/漏送，增量核对需分页、重叠时间窗口、游标与重试，并提供手动核对。[官方同步说明](https://shopify.dev/docs/apps/build/webhooks)。
3. 任务持续处理、失败告警、最后同步时间、权限失效与落后状态在后台可见。请求结束后未await的内存任务不当作可靠队列；配置独立定时执行/持久化任务消费机制。
4. 仅保存分佣必要字段，不保存完整客户档案/地址；日志和事件payload控制敏感字段及保留，给KOL导出不含买家个人信息。权限范围与受保护数据要求分别处理。
5. 最小权限：`read_orders`、优惠读取及生成新码所需的 `write_discounts`、实际需要的商品读取；读取能力以实际授予的scope为准，避免重复申请被write已涵盖的read scope。历史订单核对按app类型配置 `read_all_orders`。不申请 `write_orders`、退款或自动转账权限。[订单权限说明](https://shopify.dev/docs/api/usage/access-scopes)。
6. 默认订单权限只有最近60天；历史退款与结算核对需要更早订单访问。缺权限时阻止受影响结算并明确提示，不能拿本地旧快照声称已重核对。
7. Shopify Admin token只在服务端；API版本固定并联调项目实际版本（当前配置默认2026-07），不因文档引用latest就自动升级。Shopify自定义应用优惠等实际能力以本店测试为准。

保留策略建议：匿名访问明细90天后清理，只保留聚合与仍有关联用途的最小证据；订单归因、佣金、审计和结算记录按品牌财务/合同要求单独配置，不跟流量一起删。隐私告知/同意与具体保留期限上线前核定。CSV与合同/付款凭证引用应限制权限；链接不能代替安全文件存储。

## 13. 整体复核结论

复核覆盖佣金版本、优惠码边界、会话连续性、金额/退款、同步、结算和部署隔离；详见 [复核记录](kol-admin-review.md)。本轮已在设计中补齐：

- 自定义比例与0%/空值区分，checkout快照避免历史被新比例覆盖。
- Shopify已有码绑定与受控发码同时支持，权益引擎仍归Shopify；异步成功、活动共享规则、唯一键与远端/本地部分失败分别处理。
- 短期会话和独立checkout绑定，阻止多标签页串单、旧结账长期挂佣、码绕过链路。
- 付款与退款交易核验，含税市场/折扣分摊/免费行/非商品退款/多币种清晰计佣。
- 锁单后的退款与并发重复付款防护；停合作后负余额保留待追回。
- 主站/后台入口隔离、应用逐请求鉴权，数据卷持久化与后台直接共库。

**仍需真实联调的上线门槛，不宣称已验证或没有漏洞：** Shopify Cart引用到订单的可靠关联；真实付款/退款/争议渠道；税与多币种样本；后台入口旁路与HTTPS/IP证书；持久化任务、备份恢复及访问压力。任何一项关键链路未通过，不开放正式分佣结算。

## 15. 已确认的产品基线

1. 四页轻后台、只给品牌管理员；独立HTTPS端口，内部共用Offy应用和数据库。
2. 每位KOL自定义百分比（建议0%–100%、最多2位小数），不设固定档位；在创建checkout时锁定当单比例。
3. **已确认两种优惠码入口：绑定Shopify已有码、Offy生成新码并同步到已有活动。** 规则仍归Shopify，远端确认后才绑定/分发；不凭码计佣。
4. 仅当次链接session成交归因；建议站内无活动30分钟、checkout归因有效30分钟；通知延迟不改变真实成交时间。
5. 按商品折扣与成功退款后税前净额计佣，免费行0佣金，按交易币种分开计算和结算。
6. 建议付款后冻结30天、按月人工结算，已付后退款记负调整；锁单和付款记录可追溯。
7. 上线前完成本店Shopify、HTTPS/入口隔离、任务同步、备份恢复的真实验收。
