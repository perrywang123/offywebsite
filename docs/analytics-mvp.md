# 行为与故障分析 · 待实施方案

状态：通用分析仍为规划，2026-11-08校准。**当前没有AnalyticsProvider、/api/events、analytics_event表或analytics:report脚本。KOL专项已实现最小访问与Shopify核对，不等同全站分析。** Meta 专项已实现可选 Pixel 漏斗、关键事件 CAPI 和后台诊断，默认关闭、尚未生产启用，见 [Meta 技术方案](meta-technical-plan.md)；这不代表本通用分析方案已整体落地。

## 目标与事实边界

收集匿名页面浏览、商品点击、加购与结账发起，协助定位404、服务错误和慢请求。真实付款发生在Shopify：收入不能根据浏览器按钮、checkout跳转或return页清袋推断。

## 建议依赖顺序（非已批准排期）

1. 明确事件/保留/隐私范围，写独立OpenSpec与失败测试。
2. 先做小范围page_view与error采集、schema迁移和接收API；行为失败不能阻塞购物。
3. 再给商品/加购/Checkout接具体事件，用事件委托时要定义组件属性透传与语义，不声称只加属性即零改造。
4. 最后做可验签Shopify已付款webhook、幂等和按币种统计收入；不得在混币金额上直接求和。
5. 报表、保留清理和运维监测经过验证后再供后台使用。

## 设计候选

客户端批量sendBeacon/fetch keepalive；服务端zod、体积与速率限制、服务时间戳和去重。会话/匿名标识只解决单设备关联，不等于唯一自然人。拒绝或清洗敏感参数，不采邮箱、收货地址、支付信息或原始IP进入行为表。保留期限、同意机制和权限在实施前明确，不把旧草案的90天/60次限额视为已定或已实现。

服务端错误可从Next instrumentation/onRequestError、RouteHandler边界和not-found路径采集；middleware只见请求，不能凭请求路径可靠知道最终SSR是否404。未捕获异常监听不能吞掉致命错误后继续假装健康。

## 数据模型原则

事件类型/名称、匿名session、path、最小化props、接收时间；错误与收入事件来源可追溯。SQLite JSON查询使用json_extract等当前方言，不复制PostgreSQL ::numeric/->> 样例到运行脚本。规模与保留策略先压测再决定是否另建分析存储。

## 验收与限制

验证单条/批量、重复/乱序、阻断与断网、服务端状态、签名/重放、限流和PII清洗；客户端事件有丢失，不能给出未经测量的固定丢失率或用它作财务真值。本方案可与 [KOL控制台](admin-console.md) 共用已核验收入服务，但全站行为采集仍未实现。
