## 证据与边界

基线阶段进行了改造前源码审查，覆盖 `AdminConsole.tsx`、`CheckoutDiagnostics.tsx`、`AdminWorkspace.tsx` 和 `admin.css`。同时直接查看用户本轮提供的筛选截图，以及上一轮实际运行截图：[桌面订单](design/kol-admin/navigation/orders-1440.jpg)、[手机名单](design/kol-admin/navigation/partners-375.jpg)、[手机合作表单](design/kol-admin/partner-form/create-375.jpg)。其中手机表单截图能看到保存区覆盖“合作状态”控件下部。

基线图片部分为空的隔离数据库页面，不能用来证明有数据时的复杂界面质量。复评已增加五个栏目有数据的前后截图，覆盖模拟订单/退款/已付批次/负调整、长名称与代码、多币种和多种诊断状态。

本评审直接审查最终代码、最新截图和 `layout-matrix.json`；实际浏览器操作由主代理统一执行并反馈结果，本评审没有另行操作共享页面。45组矩阵、筛选展开/收起、日期键盘、表单保存和冻结/解除证据用于本地交互复评。它们不构成真实 Shopify 支付、生产退款、财务到账或生产部署验收。真正空数据库补证现已完成：主代理另启全新隔离库，五栏目分别在375px与1440px运行，共10组空态截图及记录。本评审核对了 [空库记录](design/kol-admin/usability-review/empty-states.json)、10个图片文件，并抽查 [手机空订单](design/kol-admin/usability-review/empty-orders-375.jpg) 与 [桌面空优惠码](design/kol-admin/usability-review/empty-codes-1440.jpg)；各页有明确无记录说明和下一步指引，页面宽度等于视口。此项与已有数据筛选后的零匹配恢复分别记证。

## 改造前的问题（保留审查基线）

基线未发现需要立即停用系统的P0交互问题。以下P1/P2描述的是改造前状态及当时的验收要求，不代表最新源码仍存在相同缺陷；实施后的处理结论见末节。

### P1：筛选区缺少一致的语义与布局

订单页三个下拉只有 `aria-label`，没有持续可见的字段标签；两项日期却单独有顶部标签。CSS 又分别为下拉、日期设置宽度和背景，形成用户截图中的不平衡。管理员需要根据“全部状态”等当前选项猜字段含义，切成某个具体值后上下文更弱。见 `AdminConsole.tsx` 的订单 `.filters` 及 `admin.css` 的 `.filters > select`、`.filters label`。

应把搜索、达人、币种、状态和付款日期视为一个有名称的筛选组。每个控件提供可见标签，控件高度一致，日期为可读的成对字段；宽屏按可用宽度整齐排布，窄屏自然换行。明确结果数量和当前筛选，并提供“清空筛选”。不必增加新的统计面板或图表。

验收：360/375/768/1440/1920px 下，控件标签、输入值和日期图标完整可读；每个控件均可经键盘访问；清空操作同时移除搜索、下拉及日期条件，不遗留不可见条件。

### P1：日期范围和无结果不能指导恢复

订单结束日期目前允许早于开始日期，用户得到的只是空订单结果。优惠码与月结的空态又按全量数组长度判断，搜索不到匹配项时会留下只有表头的空白区域。合作页有筛选空态，但没有直接清空的操作。见订单 `orders` 过滤、优惠码 `data.codes.filter` 与 `!data.codes.length`、月结 `data.settlements.filter` 与 `!data.settlements.length`。

应区分“尚无记录”“筛选无匹配”“读取失败”。无效日期明确提示字段及修正方式，不能被当成业务空数据。筛选无结果提供清空或修改条件的直接出口；显示数量应表达“当前匹配数”，避免筛选后的0被误读为系统总量为0。订单列表若只含最近500笔，必须继续保留范围说明。

验收：有数据但搜索无匹配时，五个栏目均不出现无解释的空白；日期倒置显示明确错误；清空后恢复预期记录；全量空库、筛选空集和503读取失败各有不同反馈。

### P1：手机长弹窗的保存区会遮挡表单

当前弹窗整体滚动，手机 `.dialog-actions` 使用 `position:sticky; bottom:-20px`，与表单控件共处同一流。已保存的375px截图显示保存按钮压在“合作状态”区域上。输入、错误提示、键盘弹起和展开可选区都会改变内容长度，使问题更容易重现。

应形成明确的弹窗头部、可滚动内容和操作区，或提供等价的底部安全留白。保存区可以保持易于触达，但不能遮挡控件、错误消息或最后一项字段。长说明在相关字段附近简短呈现，次要合同/收款资料保持可展开；必填与可选要持续可辨。保留 Esc、焦点限制与关闭后焦点返回行为。

验收：360×800和375×812下逐项填写合作、码、月结及操作原因表单，最后一项内容可以滚动到操作区上方；打开日期/下拉、展开可选区或触发校验错误后，控件与提交按钮均可用。200%缩放仍可操作。

### P1：重要操作确认缺少目标摘要

冻结、结束绑定、取消批次和登记付款共用的确认弹窗只显示操作标题、原因等字段。`action` 状态仅保留 `kind/id/title`，弹窗没有把目标达人、订单号、批次月份、金额与币种重新展示给操作者。用户在长列表或手机横滚后难以确认当前到底操作哪条记录。服务端有校验不等于界面足以防止选错对象。

应在确认表单顶部提供只读目标摘要。订单展示订单号与达人；优惠码展示代码与达人；月结展示达人、月份、金额及币种。登记付款继续明确“仅登记平台外付款凭证”，保留现有复核和勾选，不增加真实转账。取消/结束操作写清实际影响。

验收：从两个不同对象分别打开操作弹窗，摘要准确跟随所选记录；确认所提交的 id 与摘要一致；无令牌、未解冻或结算开关关闭等服务端条件仍然有效。

### P1：手机表格把关键操作放到屏幕外

通用表格统一 `min-width:850px`。在手机上，订单、码和月结的对象在最左侧，操作在最右侧，中间需要大幅横滚；页面没有明确滚动提示或可靠的对象上下文。诊断列表已经有手机分字段重排，反而更易完成任务。

可在手机将账簿行改为带字段标签的纵向记录，或保留可理解的局部横滚并固定必要对象上下文、给出提示。关键标准是用户不必在看不到目标对象的情况下点击动作。不能把表格整页横向撑开，也不能简单隐藏金额、币种、状态等核对必需信息。

验收：使用长达人名、长优惠码、至少两种币种、失败状态及多条记录，在手机完成查看对象→判断状态→操作的全过程；对象与金额不串行，页面本身无横向溢出。

## 可一并改善的 P2 问题

1. **错误上下文应收敛。** `error` 同时出现在页面提示和弹窗内，一些开窗入口未清理上次错误。应让表单错误留在当前表单，页面连接错误留在页面；重新打开不同操作不带旧错误。既有字段级中文原因和自动聚焦应保留。
2. **能力不可用时尽早说明原因。** 无 Admin 令牌时本地合作可用，但远程码/同步操作仍可能先打开完整表单再失败。对确实不能提交的远程动作给出邻近说明，保留本地管理入口；不新增必须配置令牌才能登录的依赖。选择合作时也应根据有效合作状态说明暂停/到期原因，不能只显示存储的 `active` 字面值。
3. **连接与同步信息按任务分层。** 当前抽屉集中权限、worker、收件箱、原始错误和审计，品牌运营较难快速判断“本地可用、Shopify是否连接、最近同步是否成功”。应先给可行动的状态摘要和重试入口，将权限列表、内部任务编号与原始错误放在进一步详情中。不要把没有错误的 worker 等同于已成功同步。
4. **手机首屏层级需要更紧凑。** 当前两行导航加较高的页头、按钮与说明，使名单内容在375px截图中很晚才出现。建议在不缩小触控目标的情况下压缩重复留白、缩短页头说明，统一主操作位置；桌面空态也不必占据过高白区。
5. **提交中的取消含义要明确。** 若允许关闭正在提交的表单，应说明关闭不等于撤销已发送的操作；若禁用取消，应保留明确的进度和失败恢复。界面不得暗示已取消实际已经写入的变更。无需为纯查询加入额外确认。
6. **面向管理员的语言统一。** 成功提示中的 `checkout`、状态中的未知错误代码、列表中的系统标识应有直白摘要；需要精确诊断时仍可展开原文。财务净额、比例快照、冻结及不同币种分开计算的语义必须保留。

## 建议按三个实际任务验收

第一个任务是新增合作并交付链接：从名单找到“新增合作”，只输入一次名称，留空社媒主页，自定义佣金，保存后找到固定链接并复制。重复名称和修改名称不得破坏既有链接；表单错误能定位且不会丢输入。这里继续采用上一轮已实现的服务端别名生成和版本规则。

第二个任务是查找并处理异常：从订单输入单号，按达人/币种/状态及日期缩小范围；误填日期时知道哪里错；没有结果时一键恢复；打开人工冻结后再次看清订单与达人再确认。诊断任务则从同一次请求的国家、商品与 Shopify 响应找到原因，原始链接按原有审计方式按需查看，不把“生成链接”显示成付款成功。

第三个任务是月结核对：先看达人及币种对应余额，再找月份/批次；执行锁单或付款登记时重新确认目标和金额。测试只在模拟财务数据上操作，真实付款和生产账本仍按现有服务端核验及人工流程处理。

所有任务都应使用360、375、768、1440和1920px检查，同时覆盖键盘、长文案、至少两种币种、真实空集、筛选空集、等待、503和401。截图与DOM测试相互补充：DOM测试验证字段、行为和对象关联；实际浏览器证明控件没有被遮挡、移动布局可用。

## 实施后复评与遗留项

### 五类P1的处理结论

**筛选语义与布局已改善。** 桌面订单的五个筛选控件有持续可见的标签、白底和一致高度。手机订单默认收起高级条件，日期同组双列。展开类名现为独立的 `filters is-expanded` / `diagnostic-advanced is-expanded` token，最终源码与实际展开截图相符；不把第一版仅有按钮但无法展开的状态计为通过。选GBP后收起仍显示“已选：币种 GBP”，返回一条对应订单；清空恢复三条模拟订单。见 [手机收起](design/kol-admin/usability-review/after-orders-375.jpg)、[展开](design/kol-admin/usability-review/after-orders-expanded-375.jpg)、[已选GBP](design/kol-admin/usability-review/after-orders-filtered-375.jpg)。

**日期及无结果恢复已改善。** 主代理通过真实原生日期键盘输入验证订单非法范围会给出错误，不显示成“暂无订单”；诊断开始2027-11-10、结束2027-11-01时显示明确提示、禁用提交并保留旧列表，清空后恢复。GB国家筛选只返回一条模拟记录。优惠码/月结无匹配提供清空并可恢复，合作表单日期错误保留输入、聚焦顶部中文提示，修正后可保存。真实空库五栏目375/1440px共10组浏览器证据现已补齐，各页区分尚无业务记录与筛选零匹配；网络错误组件测试、真实空库和筛选恢复分别记证。

**长弹窗操作区已改善。** 最终结构将头部、滚动内容和底部动作分开。375px实测最后一项 notes 输入区域约 y467–557，footer约 y698–771；底部截图可看到两者完整分离。主代理已实际完成空社媒主页合作保存。见 [顶部](design/kol-admin/usability-review/after-partner-dialog-top-375.jpg)、[底部](design/kol-admin/usability-review/after-partner-dialog-bottom-375.jpg)。这支持长表单不再被保存按钮覆盖，不能推断所有移动浏览器软键盘组合均已覆盖。

**重要操作目标摘要已实现。** 订单确认显示 `#TEST-1000 / Maya / USD 60.00`；月结确认显示 `2026-11 / Maya / USD 6.53`；结束绑定确认显示所选长代码及Maya，并说明不会停用Shopify。源码按所选id从当前读模型解析目标，原有服务端操作规则未被替换。隔离模拟订单完成了人工冻结与解除交互，未执行真实付款。见 [订单确认](design/kol-admin/usability-review/after-order-context-375.jpg)、[月结确认](design/kol-admin/usability-review/after-settlement-context-375.jpg)、[代码确认](design/kol-admin/usability-review/after-code-context-375.jpg)。

**手机账簿可达性已改善。** 375px订单、代码和月结行按带字段名称的记录呈现，金额、币种、状态与动作保持同一对象上下文；平板仍保留局部横滚。最终五页×九宽度的 [45组矩阵](design/kol-admin/usability-review/layout-matrix.json) 中文档宽度均等于视口，所测常用button/input/select没有小于44px的目标，原生checkbox按标签命中区判断。此前Maya按钮42.39px的问题已修正。矩阵不等于已验证所有展开态或200%缩放，关键展开态另有截图和操作证据。

### 剩余P2及边界

1. **手机诊断仍偏重说明和表单。** 375px订单的首条记录约在y540，已比第一版完整筛选占满首屏更易浏览；诊断首条约在y769，首屏只露出开头。保留定义和保留期限是合理的，后续可缩短常驻说明、把次要定义收进说明区，同时避免隐藏“生成链接不等于付款成功”。
2. **平板局部横滚仍有成本。** 768px及部分901–1024px布局中，账簿区域仍需横向滚动。当前已有可聚焦、有名称的局部滚动区及提示，手机P1已缓解；若平板是高频设备，可在后续使用更适合中等宽度的记录排布。
