# Boundary and user experience

用户已确认本设计。实现及正式启用状态分别记录于 tasks 与发布验收记录。

管理工作台分为三块，沿用当前视觉和侧栏：

1. **短链访问**：按合作/别名筛选，今日、近7日、累计打开次数、按日趋势、最近打开时间、采集开始时间。明示「Offy 记录，重复打开计次；不等于人数或 Collabs Visits」。历史未采集显示「未采集」，不虚填0或按Nginx请求回推真人访问。
2. **自动转化记录**：标明官方归属事件来源、原生创作者身份、订单号、接收/来源时间、同步状态，并通过 Admin API 读取订单金额、币种和付款/退款事实。同步失败保留最后成功状态并提示；没有官方佣金字段则显示「来源未提供」。不使用「订单金额×费率」冒充官方应付，也不自动将已退款解释为官方佣金已取消。
3. **报告与账单核对**：保留当前导入、修订、只读核对及付款证据。自动转化与导入报告分开列示，不将重叠来源的金额相加，不创建第二套结算。

# Short link counting

现有有效性检查、HEAD/预取/机器人处理、303目标与dt_id保留全部不变。只在成功解析出启用链接时，于响应后尽力记录一次打开请求；不增加浏览器追踪Cookie，不保存IP或完整User-Agent。使用独立聚合表，按链接ID/日期原子累计并记录最近时间，不复用旧 Offy session归因或账本。计数故障不改变原有跳转结果，不等待远端分析服务。

第一版不提供假UV。若后续需要匿名去重访客，单独定义同意、标识与统计窗口，再实施。

# Official event integration gate

实际契约已于2026-11-08在本店 Flow 编辑器核实。店内已有 Flow 和原有活跃弃单流程，没有出现新的权限授权页，无需重复安装；既有流程不改。触发器提供 `communityMemberId`、`order`、累计 `salesNumber` / `linkVisitsCumulative` / `salesCumulativeCents` / `commissionCumulativeCents` 及创作者姓名/用户名。累计金额无明确币种，作为原始快照存储和展示，不当作本笔金额或出款。原触发器没有事件时间或唯一事件 ID；另存 Flow 发送时间、服务器接收时间和订单创建时间，以店铺、官方编号和订单去重。详见 `docs/collabs-observation.md` 与最小 Liquid 模板。

安装/权限在实际授权页确认后才提交。先读取官方 Order Attributed 的变量及类型，确定订单、创作者、时间、原生金额等实际可用字段；没有字段就不写适配假设。使用专用的服务器生成入站凭据并安全配置到 Flow secrets，拒绝未授权请求，实施重试幂等与输入边界校验；不使用浏览器Cookie抓取内部Collabs接口。

保持三种身份独立：Offy别名、Flow原生创作者标识、CSV报告中的来源标识。官方身份必须有实际凭据后绑定，不从dt_id、昵称或邮箱猜测CSV标识。无法映射的事件进入「待关联」，不擅自算到某个KOL。

接收器先落库、返回确认，再异步只读查询订单。官方事件能够证明订单归属；普通订单API来源参数仅作为辅助证据，不能替代官方事件。退款及取消通过可用订单API复核，官方佣金调整、手续费及最终出款以实际官方来源为准。

工作流启用后主要接收新事件，不承诺自动回补历史。#1134的既有官方佣金明细不伪造成新Flow事件；历史回填使用可取得的真实报告。实际字段读取完成前不承诺自动同步全部佣金及出款。

# Release and validation

先按已确认的实际事件契约TDD，再做隔离HTTP/数据库/浏览器验证。覆盖重复及乱序事件、未知身份、缺失金额、多币种、网络失败、统计写入失败、HEAD/预取不计数和303参数不变。仅做读取/统计，不发起真实购买、退款或付款。

Git先推送，GitHub构建Linux镜像，服务器不编译。先备份并更新后台/worker，再单独更新主站；核对端口、Nginx及商品/结账行为。已批准范围以外的配置和业务变更另行确认。
